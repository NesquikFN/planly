# Backend Planly

Express 5 + TypeScript + Postgres через `pg`. Без ORM, без генераторов —
SQL пишется руками и живёт только в репозиториях.

Заменил собой Supabase. Ключевое отличие: браузер больше не ходит в базу.
Раньше данные защищали политики RLS, теперь — сам backend: `user_id` для
каждого запроса берётся из сессии (`req.user.id`) и никогда из тела
запроса, а каждый SQL-запрос к пользовательским данным содержит
`where user_id = $n`.

## Слои

Строго в одну сторону, вниз. Слой не должен знать про то, что выше.

| Слой | Папка | Отвечает за | Не делает |
| --- | --- | --- | --- |
| Маршруты | `src/routes/` | пути, порядок middleware | логику, валидацию |
| Контроллеры | `src/controllers/` | разбор запроса схемой Zod, код ответа | SQL, правила |
| Сервисы | `src/services/` | правила предметной области, `AppError` | SQL, знание про `req`/`res` |
| Репозитории | `src/repositories/` | SQL, snake_case ↔ camelCase | HTTP, бизнес-правила |

Валидация — `src/validation/*.schemas.ts`, отдельно от контроллеров: одна
схема нередко нужна двум маршрутам, а тесты на неё пишутся без Express.

## Файлы, которые стоит прочитать первыми

| Файл | Зачем |

| `src/app.ts` | сборка приложения: CORS, куки, заголовки, порядок middleware |
| `src/routes/index.ts` | карта всего API и того, что закрыто аутентификацией |

## API

Все ответы — JSON. Ошибка всегда в одной форме:
`{ "error": { "code": "TASK_NOT_FOUND", "message": "Задача не найдена" } }`,
у ошибок валидации добавляется `details`.

### Публичные (`/api/auth/*`, лимит по IP)

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | `/api/auth/register` | создаёт пользователя и профиль, выдаёт сессию |
| POST | `/api/auth/login` | вход по email и паролю |
| POST | `/api/auth/logout` | стирает куку сессии |
| POST | `/api/auth/password-reset` | письмо со ссылкой; всегда 204 |
| POST | `/api/auth/password-reset/confirm` | смена пароля по токену из письма |
| POST | `/api/auth/verify-email` | подтверждение почты по токену |
| POST | `/api/auth/verify-email/resend` | повторное письмо; всегда 204 |
| GET | `/api/health` | статус сервиса и доступность базы |

### Требуют сессии

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/api/me` | текущий пользователь и профиль |
| PATCH | `/api/me` | правка профиля |
| GET | `/api/tasks` | все задачи пользователя |
| POST | `/api/tasks` | создать (можно со своим `id` — клиент создаёт оптимистично) |
| PATCH | `/api/tasks/:id` | частичная правка |
| PUT | `/api/tasks/:id` | заменить целиком — восстановление из архива |
| DELETE | `/api/tasks/:id` | удалить |
| POST | `/api/tasks/import` | разовый перенос локальных задач |
| GET | `/api/calendar-events` | все события пользователя |
| POST | `/api/calendar-events` | создать событие или серию |
| PATCH | `/api/calendar-events/:id` | правка, включая `skippedDates` |
| DELETE | `/api/calendar-events/:id` | удалить (серия уносит свои переопределения) |

## Решения, которые стоит знать

**Сессия без таблицы сессий.** Токен — `base64url(payload).base64url(hmac)`,
как JWT, но без библиотеки ради двух полей. Плата: отозвать конкретный
токен до истечения нельзя, смена `JWT_SECRET` разлогинивает всех.

**Кука, а не заголовок.** Токен в httpOnly-куке недоступен из JavaScript и
виден `proxy.ts` на сервере Next.js, поэтому неавторизованного
пользователя разворачивает до рендера страницы. Заголовок
`Authorization: Bearer` тоже принимается — удобно для curl и тестов.

**Пароли на встроенном scrypt.** Не argon2 и не bcrypt: обе — нативные
модули, которые пришлось бы собирать под alpine в Docker-образе. Параметры
хранятся внутри самой строки хеша, поэтому их можно поднять позже, не
ломая уже сохранённые пароли.

**Токены писем хранятся хешами.** В `auth_tokens` лежит sha256, сам токен
существует только в письме. Гасится атомарно одним `update ... returning`,
поэтому по одной ссылке нельзя пройти дважды.

**Ответы не выдают, какие email существуют.** Запрос сброса пароля всегда
204, вход всегда `INVALID_CREDENTIALS`, а пароль проверяется даже когда
пользователя нет — иначе разница во времени ответа сама бы всё сообщала.

**Часовые лимиты — в Postgres.** Счётчик в памяти обнулялся бы каждым
деплоем сразу всем. Минутный антифлуд сознательно остаётся в памяти: окно
короткое, а поход в базу на каждый запрос дороже пользы.

## Проверки

```bash
npm run typecheck --workspace=backend && npm run lint --workspace=backend && npm test --workspace=backend
```

Тесты не ходят в базу: `src/__security__/testEnv.ts` подменяет
`DATABASE_URL` мёртвым портом, поэтому проверяется ровно то, что решается
до обращения к Postgres — аутентификация, валидация, заголовки. Логику
самих SQL-запросов такие тесты не покрывают.
