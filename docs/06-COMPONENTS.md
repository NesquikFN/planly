# 06. Components — Planly

Документ описывает организацию кода в `src/` и правила, по которым проект должен расти без превращения в хаос на протяжении многолетней разработки.

## 1. Структура каталогов

```
src/
  app/                  # маршруты / страницы приложения
  components/
    layout/             # глобальная оболочка: навигация, сайдбар, шапка
    ui/                 # переиспользуемые примитивы (кнопки, поля, диалоги)
    dashboard/          # компоненты модуля Dashboard
    tasks/               # компоненты модуля Tasks
    notes/               # компоненты модуля Notes
    projects/            # компоненты модуля Projects
    calendar/             # компоненты модуля Calendar
    ai/                   # компоненты модуля AI
  hooks/                # переиспользуемые React-хуки
  lib/                  # чистые утилиты домена (промпты, форматирование, конфиг)
  services/             # интеграции с внешним миром (API, БД, AI-провайдер)
  types/                # общие TypeScript-типы и контракты данных
  utils/                # универсальные хелперы без бизнес-логики
  styles/               # design tokens, темы, глобальные стили
```

## 2. Правила разделения ответственности

- **`components/ui/`** — не знает о бизнес-логике. Кнопка не знает, что такое "задача".
- **`components/<module>/`** — знает о бизнес-логике своего модуля, но не лезет в чужие модули напрямую (Tasks не импортирует внутренности Notes).
- **`components/layout/`** — знает о структуре приложения в целом, но не о деталях конкретного модуля.
- **`hooks/`** — связывает компоненты с `services/`, инкапсулирует состояние (loading/error/data).
- **`services/`** — единственное место, где происходят обращения к API/БД/AI. Компоненты никогда не делают запросы напрямую.
- **`lib/`** — чистые функции без побочных эффектов (форматирование дат, построение промптов, валидация).
- **`utils/`** — максимально общие хелперы, не привязанные к домену Planly (могли бы жить в отдельном npm-пакете).
- **`types/`** — общие типы данных (Task, Note, Project, Event, AIMessage и т.д.), используемые и в компонентах, и в сервисах.

## 3. Правило направления зависимостей

```
components/<module>  →  hooks  →  services  →  (внешний мир: API/БД/AI)
components/<module>  →  components/ui
components/*         →  lib, utils, types
```

Запрещено обратное направление: `services/` и `lib/` никогда не импортируют из `components/`.

## 4. Именование и структура модульных компонентов

Каждый модуль (`tasks/`, `notes/`, `projects/`, `calendar/`, `ai/`) со временем структурируется по общему паттерну:

```
components/tasks/
  TaskList.tsx
  TaskCard.tsx
  TaskForm.tsx
  ...
```

Общие для нескольких модулей паттерны (например, карточка сущности, форма создания) сначала реализуются в конкретном модуле, и только при повторном появлении в 2+ модулях выносятся в `components/ui/` — без преждевременной абстракции.

## 5. Кросс-модульные связи

Когда модулю нужны данные другого модуля (например, Dashboard показывает задачи и заметки), он обращается к соответствующим `hooks/`/`services/`, а не импортирует компоненты другого модуля напрямую. Композиция происходит на уровне `app/` или `dashboard/`.

## 6. Тесты и долгосрочная поддерживаемость

- Каждый значимый компонент/хук/сервис сопровождается тестом рядом с собой (соглашение о расположении тестов фиксируется при выборе стека).
- Публичные контракты (`types/`) меняются осторожно — это точки соприкосновения между модулями.
