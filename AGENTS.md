# Planly — инструкции для Codex

Planly — прототип персонального AI-планировщика на Next.js 16 (App Router) + React 19 +
TypeScript + Tailwind v4. Данные — только `localStorage`, бэкенда/БД/реального AI нет.

## Принцип работы

- Не сканировать весь репозиторий перед каждой задачей.
- Не читать все страницы, компоненты и stores без необходимости.
- Сначала определить область изменений (модуль → файлы → зависимости).
- Читать только файлы, непосредственно относящиеся к запросу.
- Карта для навигации, в таком порядке:
  1. Этот файл (AGENTS.md).
  2. [PROJECT_HANDOFF.md](PROJECT_HANDOFF.md) — самый свежий статус: что реализовано, что
     незавершено, следующие задачи. Читать в начале новой сессии.
  3. [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) — карта архитектуры и потоков данных (частично
     устарела после последней сессии — см. «Незавершённые задачи» в PROJECT_HANDOFF.md).
  4. [docs/MODULES.md](docs/MODULES.md) — таблица модулей: какие файлы читать для конкретного модуля.
  5. [docs/CURRENT_TASK.md](docs/CURRENT_TASK.md) — состояние текущей задачи (если она есть).
- [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md) — подробный архивный контекст одной из прошлых сессий
  (архитектурные решения, известные ограничения, история изменений). Открывать точечно, когда
  нужны детали, которых нет в ARCHITECTURE.md/MODULES.md — не читать целиком по умолчанию.
- `docs/01-PRD.md` … `docs/06-COMPONENTS.md` — **долгосрочные продуктовые документы** (видение
  на годы вперёд), НЕ описание текущего кода. Там встречаются модули/папки, которых в коде ещё
  нет (`services/`, `notes/`, отдельный `utils/`). Не путать с ARCHITECTURE.md/MODULES.md.
- Реальный код — источник истины. Документация — навигация, а не замена проверки кода.

## Ограничение области задачи

Перед изменениями определить:

- целевой модуль (см. таблицу в MODULES.md);
- конкретные файлы;
- прямые зависимости (импортируемые hooks/lib/types/ui-компоненты);
- возможное влияние на общие компоненты (Sidebar, Header, ui/*, stores).

Не открывать несвязанные модули без необходимости.

Пример: задача про страницу Projects — разрешено читать файлы Projects (страница, компоненты,
типы), общие UI-компоненты, которые они импортируют. Не читать Calendar, Dashboard-специфичные
stores и т.д., если задача их не затрагивает.

## Перед началом работы

Кратко сообщить:

1. Какой модуль будет изменён.
2. Какие файлы планируется изучить/менять.
3. Почему они нужны.

Не проводить длинный общий аудит проекта. Расширять область чтения только тогда, когда без
этого невозможно выполнить задачу — и коротко объяснять причину перед расширением.

## Правила изменений

- Не создавать дублирующие компоненты.
- Не создавать новый store, если существующий можно расширить.
- Не менять глобальную архитектуру (порядок Provider'ов в `layout.tsx`, модель `CalendarEntry`)
  ради локальной задачи.
- Не рефакторить несвязанные файлы.
- Не добавлять функции, которых пользователь не просил.
- Не заменять рабочие части приложения.
- Не использовать моковые данные вместо существующих реальных данных/stores.
- Для UI-скелета разрешены локальные демонстрационные данные, если пользователь явно просит
  только скелет (как сейчас сделано в Projects — `lib/projects-mock-data.ts` + `useState`, без
  стора и без localStorage).
- Сохранять визуальный стиль Planly (см. `styles/globals.css`, Tailwind-классы существующих
  компонентов).
- Сохранять существующую работу светлой и тёмной темы (`useTheme()`, класс `dark` на `<html>`).
- Не ломать localStorage и существующие данные (ключи `planly:*`, см. ARCHITECTURE.md).
- Все новые тексты интерфейса — на русском.

## Git

- Не выполнять `git add`.
- Не выполнять `git commit`.
- Не выполнять `git push`.
- Не создавать pull request.
- Выполнять Git-команды только по прямой просьбе пользователя.

## Проверка

После изменений:

- проверить только затронутый функционал;
- запустить `npm run build` (если параллельно работает `npm run dev`, учитывать конфликт кэша
  Turbopack — см. PROJECT_CONTEXT.md §13.4, при проблемах предложить `rm -rf .next`);
- исправить ошибки, вызванные текущими изменениями;
- не исправлять посторонние проблемы без запроса.

## Финальный отчёт

Указать:

- изменённые файлы;
- созданные файлы;
- реализованные действия;
- использованные заглушки/моки;
- результат сборки;
- оставшиеся ограничения.
