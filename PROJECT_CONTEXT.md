## 1. Назначение Planly

Planly — коммерческий прототип персонального AI-планировщика: задачи + заметки (пока не реализованы) +
проекты (пока не реализованы) + календарь в одном интерфейсе, с AI-ассистентом «на будущее» (сейчас его
нет, только заглушка ввода). Позиционирование — «самый простой AI-планировщик».

На данный момент это **не подключённый к бэкенду прототип**: все данные тестовые/локальные, хранятся в
`localStorage` браузера. Реального AI, базы данных и авторизации нет и пока не планируется в ближайших
задачах.

## 4. Основные страницы, компоненты и stores

### Страницы
- **`/` (Dashboard)** — `src/app/page.tsx`: Sidebar, Header, StatsRow, TaskListCard, FocusCard,
  ProgressCard, TodayCalendarCard, BottomInput, TaskEditModal, CompletedTaskToast. Есть внутреннее
  переключение `view: "dashboard" | "completed"` (список выполненных задач) через `useTasksStore().view`.
- **`/calendar` (Calendar)** — `src/app/calendar/page.tsx`: Sidebar, Header, CalendarSidebarPanel
  (мини-календарь + список календарей + «Предстоящие»), CalendarToolbar (День/Неделя/Месяц/Повестка +
  Фильтр + Добавить), сама сетка (DayView/WeekView/MonthView/AgendaView через CalendarViewTransition),
  EventDetailsPanel, EventModal, CalendarFormModal, DeleteCalendarDialog.

### Stores (все — React Context + Provider, паттерн одинаковый везде)

- **`useClock()`** (`hooks/useClock.tsx`) — отдаёt `{ now, today, todayKey }`. `now` тикает раз в минуту
  + на фокус/видимость вкладки; `today` — стабильный `Date` (пересоздаётся только при смене календарного
  дня, не каждую минуту).
- **`useTasksStore()`** (`hooks/useTasksStore.tsx`) — задачи, фокус дня, фильтры/сортировка списка,
  анимация выполнения (grace-период 500мс + fade-out), тост отмены, режим `dashboard/completed`.
  Хранит в localStorage: `planly:tasks`, `planly:focus`.
- **`useCalendarStore()`** (`hooks/useCalendarStore.tsx`) — календари, события, навигация по
  День/Неделя/Месяц/Повестка, фильтры, drag-and-drop, объединённые «entries» (события + задачи).
  Внутри вызывает `useTasksStore()` — **обязан монтироваться внутри `<TasksProvider>`**.
  Хранит в localStorage: `planly:calendars`, `planly:events`.
- **`useNotificationsStore()`** (`hooks/useNotificationsStore.tsx`) — центр уведомлений. Внутри вызывает
  и `useTasksStore()`, и `useCalendarStore()` — **обязан монтироваться внутри обоих**.
  Хранит в localStorage: `planly:notifications`.

Порядок вложенности провайдеров в `layout.tsx` жёстко завязан на эти зависимости — менять его без
понимания цепочки нельзя.

## 6. Что реализовано частично / упрощено

- **Заметки и Проекты** — только пункты меню в Sidebar, ведут в никуда (страниц нет).
- **AI** — BottomInput парсит текст простыми `includes()`-эвристиками, реального AI/LLM нет.
- **Приоритет задачи (`priority: overdue/important/upcoming/none`)** — отдельное поле, не всегда
  синхронизировано с реальной датой (часть моковых задач имеет только `dueLabel`-текст без реальной
  `date`, специально, чтобы не расходились текст и дата — см. раздел 9).
- **Уведомления «скоро»** — фиксированное окно 2 часа, только для задач с явным временем; «просрочено»
  считается по дате, не по времени суток (задача на сегодня с прошедшим временем не становится
  «просроченной» до полуночи).
- **«Только задачи/события» в фильтре календаря** — переопределены на уровне kind (`task`/`event`) в
  сторе, а не на уровне отдельных `CalendarEvent.task`-поля.
- Прочитанное, но удалённое пассивное уведомление может «вернуться» при следующей перезагрузке, если
  условие всё ещё истинно (id стабилен, не дубликат, но может путать пользователя).

## 9. Известные ошибки и ограничения

- Скриншот-инструмент браузерного preview периодически не работает в этом окружении («Browser pane is
  not displayed») — это ограничение окружения, не баг приложения. Проверка функциональности в таких
  случаях делалась через `javascript_tool`/`get_page_text`/DOM-инспекцию вместо скриншотов.
- Синтетические `PointerEvent`, отправленные через `dispatchEvent()`, не считаются браузером «настоящим»
  указателем — `setPointerCapture()` кидает исключение и раньше «съедал» весь последующий код в
  обработчике. Уже пофикшено — `setPointerCapture` обёрнут в `try/catch` во всех местах drag-логики
  (`EventBlock.tsx`, `MonthView.tsx`). Это одновременно и фикс для тестирования, и защита от реальных
  edge-case сбоев браузера.
- Консоль браузера в этой dev-сессии иногда показывает **устаревшие** ошибки из истории (например, «модуль
  не найден» для файла, который на самом деле уже давно создан) — это накопленная история WebSocket HMR
  соединения, а не текущее состояние. Всегда проверяй актуальность через `preview_logs` (реальные логи
  сервера) и свежий `get_page_text`/сетевые запросы, а не только `read_console_messages`.
- 5 из 14 моковых задач (`id: 1,3,4,5,6,7`) имеют реальную `date` (относительно текущего дня при
  старте сессии), остальные (`2,8,9,10,11`) — только текстовый `dueLabel` без `date`, специально, чтобы
  не показывать в календаре записи с датой, не совпадающей с текстом.

## 10. Важные архитектурные решения

1. **Все Provider-стор монтируются глобально в `layout.tsx`**, а не на отдельных страницах. Причина:
   `TodayCalendarCard` на Dashboard должен видеть данные календаря, а `CalendarProvider` должен видеть
   задачи — без общего родителя в дереве это невозможно. Порядок вложенности: Clock → Tasks → Calendar →
   Notifications (каждый следующий физически зависит от предыдущих через `useXStore()` внутри своего тела).
2. **Единая дата** — весь проект обязан брать `today`/`now` из `useClock()`, а не звать `new Date()`
   напрямую внутри сторов/эффектов с бизнес-логикой. Точечные самодостаточные утилиты
   (`isToday`/`isYesterday`/`isTomorrow` в `date-utils.ts`) допустимо вызывать с неявным `new Date()`,
   т.к. они предназначены для разовых точечных проверок вне сторов.
3. **`CalendarEntry` как единая модель** (`lib/calendar-entries.ts`) — календарь не хранит две отдельные
   коллекции, а на лету мёржит `CalendarEvent[]` и `Task[]` (с датой) в нормализованный
   `CalendarEntry[]` с полями `kind: "event" | "task"`, `sourceId`, `id` (стабильный, с префиксом
   `event:`/`task:`). Никакого дублирования данных, никакой отдельной синхронизации — один источник
   правды на каждую сущность.
4. **`hydrated`-гейт перед диффингом** в `useNotificationsStore` — обязательно ждать, пока ВСЕ апстрим-
   сторы (`tasksStore.hydrated && calendarStore.hydrated`) закончат читать localStorage, иначе подмена
   mock-данных на сохранённые при первой загрузке выглядит как всплеск фейковых уведомлений о
   «выполнении»/«удалении».
5. **Фокус дня хранится как `{taskId, source: "manual"|"auto", dateKey}`**, а не просто `taskId` — чтобы
   отличать «пользователь выбрал сам» (переживает смену дня) от «система предложила» (сбрасывается на
   новый день и пересчитывается).
6. **`completedAt` (ISO datetime) отдельно от `date`/`time`** (локальная календарная дата) — временная
   метка события «когда фактически выполнено» не должна путаться со «когда было запланировано».
7. **Drag-and-drop без библиотек** — всё на нативных Pointer Events + `createPortal` для «призрака»,
   следующего за курсором.

## 11. Правила работы с датами, localStorage, задачами и календарём

### Даты
- **Никогда** не использовать `date.toISOString().slice(0, 10)` для локальной даты — сдвигает день из-за
  UTC. Использовать `getLocalDateKey(date)` (алиас `toISODate`, живёт в `lib/date-utils.ts`).
- Хранить date-only значения как строку `"YYYY-MM-DD"` (локальный календарный смысл). Для точного момента
  времени (например, `completedAt`) — полноценный ISO datetime через `new Date().toISOString()`.
- Парсить `"YYYY-MM-DD"` обратно в `Date` только через `fromISODate()` (делает `new Date(y, m-1, d)`,
  локально) — никогда не `new Date("YYYY-MM-DD")` (парсится как UTC-полночь, отличается от локальной).
- Неделя — понедельник–воскресенье (`startOfWeekMonday`/`endOfWeekSunday`).
- День/месяц/день недели — всегда на русском, с заглавной буквы (`formatRussianDate`,
  `formatShortDate`, `formatMonthYear`).

### localStorage
Ключи (все с префиксом `planly:`):
- `planly:tasks` — массив задач
- `planly:focus` — `{ taskId, source, dateKey } | null`
- `planly:calendars` — массив календарей (личные/цвета/видимость)
- `planly:events` — массив реальных событий календаря
- `planly:notifications` — массив уведомлений

Никаких других ключей быть не должно — если появляется что-то новое, это, скорее всего, ошибка
дублирования данных. Каждый Provider хранит **только своё**, ничего не копирует из другого стора.

### Задачи ↔ Календарь
- Задача с `date` — автоматически видна в календаре (как `CalendarEntry` с `kind: "task"`).
- Задача без `date` — в календаре не отображается никогда.
- Задача с `date`, но без `time` — отображается как запись «Весь день».
- Задача с `date` и `time` — во временной сетке в соответствующем слоте.
- Перенос задачи в календаре (drag) → `tasksStore.rescheduleTask(id, date, time)` → меняет и `date`, и
  `time`, и пересчитывает `dueLabel` через `formatTaskDueLabel`.
- Редактирование даты/времени задачи в модалке (Dashboard) видно в календаре мгновенно и наоборот — это
  один и тот же массив `tasks`, никакого ручного «синка».
- Единственный путь редактирования любой сущности «в календаре» — `useCalendarStore().openEntryEditor(entry)`,
  который сам решает, открыть ли `EventModal` (для события) или `tasksStore.startEditing()` (для задачи).
  **Не добавлять второй путь редактирования** — раньше это уже приводило к дублирующимся кнопкам
  «Изменить».

## 13. Инструкция для нового чата Claude

1. **Прочитай этот файл целиком** перед любыми изменениями — он заменяет повторный анализ проекта.
2. **Не выполняй `git` команды автоматически** — ни `add`, ни `commit`, ни `push`, ни `reset`, ничего.
   Коммит делается **только** по прямой явной просьбе пользователя с конкретным текстом сообщения.
3. **После каждой крупной задачи** (не после каждой мелкой правки) обязательно:
   - `npx tsc --noEmit` для быстрой проверки типов,

   - ручная проверка в браузере (preview-инструменты), а не только «должно работать».
4. Если запущен dev-сервер и нужно сделать `npm run build` — **сначала останови dev-сервер**, потом

   dev/build кэша Turbopack уже один раз приводило к сессии, полностью посвящённой диагностике «битого»
   `.next`.
